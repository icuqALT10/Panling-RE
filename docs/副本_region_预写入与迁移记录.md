### 2026-10-17 入场函数

副本 JSON 可配置 `"into_function": "plre:instances/shihuang/into"`，省略、`null` 或空字符串均表示不执行副本专属入场函数。每位玩家成功传送后先执行统一的 `plre:instances/into_load`，再执行 `into_function`，两者均以该玩家为 `@s`、使用传送后的维度和位置，随后启动控制器。多人入场逐人执行，重复进入再次执行，入场校验失败不执行。

始皇已配置上述入场函数。通关只执行 JSON 的 `success` 回调，移除了控制器额外调用 `plre:instances/shihuang/reward` 的逻辑；数据包中的函数文件保留。

### 2026-10-16 入场朝向与多人分散

副本定义支持 `"rotation": [yaw, pitch]` 和 `"safe_distance": 3`。角度单位为度；yaw 为水平朝向，pitch 为俯仰（-90 至 90），例如 `[0, 0]` 表示朝南平视。按用户后续要求，不写 `rotation` 时默认 `[0, 0]`，不再保留入场前视角。

`safe_distance` 是以当前槽位的 `player_spawn_pos` 为中心的水平圆形半径，不是玩家之间的间距。半径大于零时，按配置的 Y 高度选取落点，检查站立碰撞箱、脚下支撑、世界/副本边界、液体和常见伤害方块。首名玩家优先落在中心，其他玩家优先远离已分配位置，中心间距至少 1 格且碰撞箱不重叠。先为整队规划成功再传送；落点不足会提示并拒绝本次入场，不消耗槽位、不改变成员身份或传送部分玩家。省略或设为 0 时沿用原来的固定落点行为。

当前始皇 JSON 中用户添加的 `[0, 0]` 与半径 3 保持原样并已接入。配置仍通过副本定义重载流程生效；活跃会话结束后才切换定义。验证覆盖旧配置、角度/半径无效值、单人居中、三人共享槽位且互不重叠、障碍/坑洞/熔岩避让和空间不足时整队拒绝；独立 GameTest 日志位于 `tmp/instance_arrival_20261016/tests.log`。

### 2026-10-16 人数限制与可选字段默认值

三个字段均可省略：`rotation` 默认 `[0, 0]`，`safe_distance` 默认 `0`，`player_limit_count` 默认 `1`。

- `"player_limit_count": 5`：允许 1 至 5 人，选中 6 人时全队不传送。
- `"player_limit_count": {"min": 3, "max": 5}`：允许 3 至 5 人，低于下限或超过上限时全队不传送。
- 人数必须是正整数，区间要求 `1 <= min <= max`；缺失区间端点、小数、字符串和超出 int 范围的值会使该定义加载失败，并在日志中说明配置错误。

限制应用于同一次选择器得到的去重玩家人数。在查找/消耗副本槽位、分配落点或修改玩家身份之前校验。拒绝原因包含人数限制及实际选中人数，发送给目标玩家，也反馈给不在队内的命令执行者/控制台。用户给始皇配置的整数 `5` 保持原样；其他未填写该字段的副本默认最多 1 人。

独立服务器测试覆盖默认、整数、区间三种配置各自选中 1/2/3/5/6 人的 15 种组合，检查边界成功、整队拒绝、槽位和位置不变、命令执行者收到正确提示，以及省略朝向时统一归零。日志：`tmp/instance_arrival_20261016/limits-tests.log`。

2026-10-15：`/plre instance start <instance_id> [players]` 支持玩家选择器；省略时仅进入执行者（等同 `@s`），控制台需明确指定玩家。例如 `/plre instance start shihuang @a[distance=..10]` 将选中的玩家送进同一槽位，执行者只有被选中才会加入。选中成员已在副本时整次请求失败，不会让部分玩家先进入。

同队共享机关、怪物和进度，每 tick 只更新一次控制器。死亡、退出或越界只淘汰本人，最后一名成员淘汰才失败；胜利回调逐个作用于剩余队员。退出强制死亡前先清理成员身份和 `panlingre.instance.active`，重生时也会清掉无对应会话的遗留标记。

- `instance_regions/*.nbt` 保存原生 Minecraft 烘焙后的 `FULL` 区块、光照、方块实体、机关实体及空白区块原型。压缩后的五份资源合计约 604 KB。
- 解压和坐标转换使用 Minecraft 的 IO 线程池。区块、实体、POI 的写入通过当前世界自己的存储 worker 排队，生成对应 `.mca`，不替换仍被 Minecraft 打开的文件。
- 复制时同时更新区块坐标、方块实体坐标、计划刻、实体位置、UUID 和墓室机关归属标记。
- 目标区域必须没有正在加载、已加载或等待卸载的区块及实体。整批新数据先排入存储队列，后续加载可读到待写的新数据；磁盘同步成功后才发布 READY。
- 场景结束后先等待卸载再重置。该区域仍有人或仍有加载票据时，先处理其他区域，不覆盖活跃场景；这些被阻塞的重置不计入可用备用库存，库存耗尽后的进入请求会分配更远的独立区域。
- 存档记录已分配槽位和准备版本。重新打开世界可以复用已写好的库存；本版建筑版本为 2。
- 每次重建都完整覆盖场景独占区域的全部 1024／2048 个区块：新建筑以外填空白区块，同时清除旧实体和 POI 记录，不保留旧建筑超出新建筑范围的部分。使用原生存储接口覆盖，无需删除游戏已打开的 `.mca` 文件。
- 提高定义中的 `arena_version` 会让旧准备状态失效；它独立于烘焙资源内的版本标记。关闭世界后删除 `data/panlingre_instances.dat`，下次启动会重新准备初始库存；之前扩容的位置再次分配时同样完整覆盖。
- 地图模板更新器不覆盖 Z≥2048 的副本区域，也不覆盖 `panlingre_instances.dat`。Z=1536～2047 的边界区域只剔除旧副本区块，保留地图部分。

预写入消除了首次逐块建造和世界生成、光照计算的开销。进入时仍有正常区块读取、实体加载、网络传输和客户端网格构建成本；不能把这些成本称为完全消失。始皇控制器的初始化分批加入区块票据。

## 烘焙来源

本版在独立的新空白 GameTest 世界中，使用项目原有 Gradle、Minecraft 的结构放置和保存流程烘焙五份正式结构。始皇陵额外初始化了 10 个机关显示实体。保存后提取完成光照的 FULL 区块；区域余下位置由同一空白世界的已完成区块原型填充。

`instance_regions/manifest.json` 记录源结构和烘焙资源的 SHA-256。以后修改建筑或初始机关布局时，需要重新走原生放置、光照和保存流程导出烘焙数据，并同步提高建筑版本；只改结构 `.nbt` 不会改变已烘焙的场景。
